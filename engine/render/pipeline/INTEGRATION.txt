CROSS-LANE GAPS / ISSUES TO FILE
═══════════════════════════════════════════════════════════════════════

Issue lane09-001 — Against lane 07 (gpu)
  Title: PublicGpu.h lacks cmd encoder APIs needed by render-pipeline
  Body : PublicRenderPipeline::render() needs the following primitives
         to encode real draws (M2 forward+ ship target):
           - cmd_begin_render(cmd, colour_targets[], depth_target)
           - cmd_end_render(cmd)
           - cmd_bind_pipeline(cmd, shader::PipelineHandle)
           - cmd_bind_vertex_buffer(cmd, slot, buffer, offset)
           - cmd_bind_index_buffer(cmd, buffer, format, offset)
           - cmd_bind_storage_buffer(cmd, set, slot, buffer)
           - cmd_bind_uniform_buffer(cmd, set, slot, buffer)
           - cmd_bind_texture(cmd, set, slot, texture, sampler)
           - cmd_set_viewport(cmd, x, y, w, h)
           - cmd_set_scissor(cmd, x, y, w, h)
           - cmd_draw_indexed(cmd, index_count, instance_count, first_index,
                              vertex_offset, first_instance)
           - cmd_draw_indexed_indirect(cmd, indirect_buffer, offset,
                                       draw_count, stride)
           - cmd_dispatch(cmd, gx, gy, gz)
           - cmd_pipeline_barrier(cmd, src_stage, dst_stage, ...)
         Without these, every encode_*() in lane 09 is a diagnostic-only
         stub and the lane 07 Metal backend's default cmd_submit
         (animated clear) is what the user sees on screen — M0 behaviour
         only. We are blocked on this contract before M1/M2 ship.

Issue lane09-002 — Against lane 07 (gpu)
  Title: Pass psy::gpu::Device* through render::pipeline::PipelineDesc
  Body : The PublicRenderPipeline.h contract is frozen and does NOT
         carry a Device pointer. Lane 09 currently uses a process-wide
         `set_device_hook(Device*)` shim (not part of the public surface)
         set by the orchestrator before pipeline::create(). The proper
         fix is to extend PipelineDesc { gpu::Device* device; } in a
         coordinated cross-lane change. Requires:
           - PublicGpu.h forward decl visibility (already there)
           - PublicRenderPipeline.h amended (frozen contract change,
             orchestrator must coordinate the cascade to any dependent
             lane — currently none).

Issue lane09-003 — Against lane 06 (scene)
  Title: Publish canonical render-side component schema in GxComponents.h
  Body : Extract.cpp expects a TransformWS + MeshRef + MaterialRef
         schema to walk the World for renderables. Until lane 06 ships
         engine/scene/GxComponents.h (referenced in the orchestrator
         briefing for this lane but not yet present in main), the M2+
         ECS extract is commented-out pseudocode. Lane 09 falls back to
         the M1 hardcoded triangle which is fine for M1 acceptance but
         blocks M2 (PBR sphere with multiple instances).

Issue lane09-004 — Against lane 08 (shader)
  Title: GraphicsPipelineDesc lacks vertex-layout descriptor
  Body : PublicShader.h::GraphicsPipelineDesc has a comment "// Vertex
         layout supplied via a separate descriptor (TBD by lane 09)" but
         no field. Lane 09 needs to declare its Vertex format
         (POSITION/NORMAL/UV/COLOR) to lane 08's pipeline factory so the
         right input-assembly state is set. Suggest:
           struct VertexInputAttr { uint location; uint binding;
                                    uint8_t format; uint32_t offset; };
           struct VertexInputBinding { uint binding; uint stride; };
           uint32_t vertex_binding_count;
           VertexInputBinding vertex_bindings[8];
           uint32_t vertex_attribute_count;
           VertexInputAttr vertex_attributes[16];
         Aligns with both vkPipelineVertexInputStateCreateInfo and
         MTLVertexDescriptor.

Issue lane09-005 — Against lane 11 (render-post)
  Title: Coordinate HDR colour attachment ownership
  Body : The opaque pass at M2 wants to write into an HDR R16G16B16A16
         (or Rgba16Float) colour attachment that lane 11's bloom + tonemap
         pass then reads. Right now OpaquePass.cpp targets the swapchain
         (Bgra8Srgb) directly; the right path is:
           lane 11 owns the HDR attachment lifecycle (it's the consumer)
           lane 09 writes into it with a format that lane 11 declares
         Need to align on whose Public*.h declares the HDR target +
         the format. Tracking for M2 ship.

LIMITATIONS / DEFERRED TO M3+
═══════════════════════════════════════════════════════════════════════

  * Mesh-shader path (Turing+, RDNA2+, M3+) — deferred to M9 per the
    briefing; legacy vertex/index pipeline is what M2 ships.
  * Reverse-Z depth convention — current scaffold uses standard 0=near
    / 1=far. Reverse-Z (1=near / 0=far) lands with M3 precision pass.
  * Frames-in-flight > 1 — lane 07 M0 is single-buffered; this lane's
    per-frame state is single-buffered to match. M3 work in lane 07.
  * Indirect-draw count (vkCmdDrawIndexedIndirectCount /
    MTLIndirectCommandBuffer) — placeholder in gpu_cull.slang writes
    one record per visible instance; the real count-driven draw lands
    when lane 07 ships the indirect APIs (Issue lane09-001 covers this).
  * Cluster light culling currently writes zero counts (scaffold) —
    the cluster AABB build pass + per-cluster sphere-vs-AABB test is
    M2 ship work that depends on Issue lane09-001 for the dispatch
    encode and on the orchestrator landing a real light source via
    lane 06 ECS query (Issue lane09-003).
  * Material system — fragment shader compiles with a single material
    block. Per-instance material lookup table is M3 work.
